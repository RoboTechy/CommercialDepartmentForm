# فرم مشترک دفتر فنی بهره‌بردار / انبار کارفرما / بازرگانی غدیر

وب‌سرویس ثبت درخواست کالا به‌صورت یک جدول مشترک (شبیه اکسل): هر **ردیف** یک درخواست کالاست که
ستون‌هایش بین سه بخش تقسیم شده. هر بخش فقط ستون‌های مخصوص خودش را می‌بیند و می‌تواند تکمیل/ویرایش
کند (بر اساس عضویت گروهی در **LDAP**)، و **هر تغییری روی هر فیلدی به‌طور کامل لاگ می‌شود** (چه کسی،
چه زمانی، چه مقداری را به چه مقداری تغییر داد). کل سرویس داخل **Docker** اجرا می‌شود و داده‌ها در
یک دیتابیس **SQLite** ذخیره می‌شوند. تاریخ‌ها به تقویم **شمسی (جلالی)** هستند.

## بخش‌ها و دسترسی‌ها

| بخش | کلید داخلی | گروه LDAP پیش‌فرض | می‌تواند ردیف جدید بسازد؟ |
|---|---|---|---|
| دفتر فنی بهره‌بردار | `tech_operator` | `tech_operator` | ✅ بله (تنها بخشی که این اجازه را دارد) |
| انبار کارفرما | `warehouse` | `warehouse` | ❌ خیر |
| بازرگانی غدیر | `commercial` | `commercial` | ❌ خیر |

کاربری که عضو گروه `formadmin` باشد (قابل تغییر با `LDAP_GROUP_ADMIN`) به همه‌ی ستون‌ها دسترسی کامل
دارد. سایر کاربران فقط ستون‌های بخش خودشان را به‌صورت قابل‌ویرایش می‌بینند؛ بقیه‌ی ستون‌ها را فقط
مشاهده می‌کنند. این کنترل هم در رابط کاربری و هم سمت سرور (روی هر درخواست POST) اعمال می‌شود، پس
حتی با دستکاری مستقیم درخواست HTTP هم قابل دور زدن نیست.

### فیلدهای هر بخش

**دفتر فنی بهره‌بردار** (روی ایجاد ردیف تکمیل می‌شود): شماره درخواست کالا، شرح کالا، اولویت
(A++‎/A+‎/A/B/C/D)، تعداد کل، واحد، محل مصرف، تاریخ تحویل درخواست به انبار، نوع کالا (استاندارد/ساخت).

**انبار کارفرما**: شماره درخواست خرید، مجری خرید (بازرگانی غدیر بهاباد/تهران/برنا)، شماره نامه
ارسالی به تهران، تاریخ ارسال نامه، وضعیت (تامین شده/تامین نشده/باطل شده)، تاریخ ورود به سایت.

**بازرگانی غدیر**: تاریخ ارجاع به کارشناس خرید، تاریخ مجوز پرداخت، توضیحات.

هر فیلد تاریخ یک دکمه‌ی «امروز» دارد (تاریخ سیستم را به‌صورت شمسی خودکار پر می‌کند) و همچنین قابل
ویرایش دستی است (فرمت `1403/05/12`).

## تاریخچه‌ی تغییرات (لاگ)

- روی هر ردیف دکمه‌ی «تاریخچه» هست که فقط تغییرات همان ردیف را نشان می‌دهد.
- صفحه‌ی سراسری «تاریخچه‌ی کامل تغییرات» (لینک بالای هر صفحه) همه‌ی تغییرات همه‌ی ردیف‌ها را نشان
  می‌دهد و قابل جستجو/فیلتر است: بر اساس کاربر (نام کاربری یا نام نمایشی)، فیلد، شماره ردیف، و
  بازه‌ی تاریخی (از–تا).
- هر دو صفحه برای همه‌ی کاربران قابل مشاهده و جستجو هستند، صرف‌نظر از بخششان.

## جستجو، فیلتر و چاپ

- در صفحه‌ی اصلی، بالای هر ستون یک فیلتر هست (متنی برای فیلدهای آزاد، کشویی برای فیلدهای انتخابی،
  و «از–تا» برای فیلدهای تاریخ).
- دکمه‌ی «چاپ نتایج» در صفحه‌ی اصلی، همان جدول فیلترشده را چاپ می‌کند.
- دکمه‌ی «چاپ این ردیف» در صفحه‌ی جزئیات هر ردیف، فرم کامل آن ردیف را چاپ می‌کند.
- صفحه‌ی تاریخچه‌ی کامل هم دکمه‌ی چاپ نتایج فیلترشده را دارد.

## اجرا با Docker (شامل یک سرور LDAP تستی)

```bash
docker compose up --build
```

این دستور سرویس‌های زیر را بالا می‌آورد:

- **openldap** – یک سرور OpenLDAP تستی با کاربران و گروه‌های نمونه
- **ldap-init** – سرویس یک‌باره‌ای که کاربران/گروه‌های تستی را داخل OpenLDAP بارگذاری می‌کند
- **phpldapadmin** – پنل مدیریت وب برای مشاهده کاربران LDAP در آدرس http://localhost:8081
  (Login DN: `cn=admin,dc=example,dc=com` رمز: `adminpassword`)
- **web** – وب‌سرویس اصلی، در آدرس http://localhost:3000

### کاربران تستی

| نام کاربری | رمز عبور | دسترسی |
|---|---|---|
| `tech1` | `tech1Pass1` | دفتر فنی بهره‌بردار (ایجاد ردیف + تکمیل ستون‌های خودش) |
| `oper1` | `oper1Pass1` | دفتر فنی بهره‌بردار (همان گروه `tech1`، برای شبیه‌سازی چند نفر در یک دفتر) |
| `wh1` | `wh1Pass1` | انبار کارفرما |
| `com1` | `com1Pass1` | بازرگانی غدیر |
| `admin1` | `admin1Pass1` | دسترسی کامل به همه‌ی بخش‌ها (مدیر سیستم) |

با `tech1` وارد شوید، یک ردیف جدید بسازید، و ببینید فقط ستون‌های «دفتر فنی بهره‌بردار» برایتان
قابل‌ویرایش است. با `wh1` یا `com1` وارد شوید تا تکمیل ستون‌های خودشان روی همان ردیف را ببینید.

## اتصال به سرور LDAP واقعی سازمان (Active Directory یا OpenLDAP)

سرویس‌های `openldap`، `ldap-init` و `phpldapadmin` در `docker-compose.yml` فقط برای تست/دمو هستند.
برای اجرای واقعی روی سرور:

1. این سه سرویس را از `docker-compose.yml` حذف (یا کامنت) کنید.
2. متغیرهای محیطی زیر را در سرویس `web` با اطلاعات LDAP واقعی سازمان جایگزین کنید:

   - `LDAP_URL` – آدرس سرور LDAP سازمان، مثلاً `ldaps://ldap.company.local:636`
   - `LDAP_BIND_DN` / `LDAP_BIND_PASSWORD` – یک حساب سرویس با دسترسی فقط-خواندنی جهت جستجو
   - `LDAP_USER_BASE` – DN پایه‌ی جستجوی کاربران، مثلاً `ou=Users,dc=company,dc=local`
   - `LDAP_GROUP_BASE` – DN پایه‌ی جستجوی گروه‌ها
   - `LDAP_USERNAME_ATTRIBUTE` – در Active Directory معمولاً `sAMAccountName`
   - `LDAP_GROUP_TECH_OPERATOR` / `LDAP_GROUP_WAREHOUSE` / `LDAP_GROUP_COMMERCIAL` / `LDAP_GROUP_ADMIN`
     – نام (`cn`) گروه‌های واقعی سازمان که هر بخش را نمایندگی می‌کنند

3. گروه‌های سازمانی شما باید از نوع `groupOfNames` (دارای ویژگی `member` با DN کامل کاربر) باشند؛
   اگر سازمان شما از گروه‌های `posixGroup` (ویژگی `memberUid`) استفاده می‌کند، فیلتر جستجوی گروه در
   `src/ldap.js` باید متناسب با آن تغییر کند (فقط چند خط).
4. برای Active Directory معمولاً از `ldaps://` (پورت 636) با گواهی معتبر استفاده کنید.
5. یک `SESSION_SECRET` تصادفی و طولانی برای محیط تولید تنظیم کنید.

## نکات فنی مهم برای استقرار واقعی روی سرور

- داده‌ها در یک فایل دیتابیس SQLite (`data/app.db`) نگهداری می‌شوند، داخل همان `volume` که در
  Dockerfile/docker-compose جدا از ایمیج تعریف شده. برای حجم بسیار بالا یا چند نمونه (replica)
  هم‌زمان از سرویس با نوشتن سنگین، می‌توان به PostgreSQL مهاجرت کرد؛ برای یک ابزار داخلی سازمانی با
  چند بخش، SQLite کاملاً کافی است.
- سشن کاربران در حافظه (MemoryStore) نگهداری می‌شود؛ اگر بیش از یک نمونه (replica) از سرویس اجرا
  می‌کنید، باید از یک session store مشترک (مثل Redis) استفاده کنید.
- تمام تاریخ‌ها به‌صورت رشته‌ی شمسی یکنواخت `YYYY/MM/DD` (و برای لاگ‌ها همراه با ساعت) ذخیره
  می‌شوند تا جستجوی بازه‌ای با مقایسه‌ی رشته‌ای ساده و درست کار کند.
- هیچ فیلدی حذف نمی‌شود و هیچ ردیفی قابل حذف نیست (فقط ایجاد و ویرایش)؛ این طراحی عمدی است تا
  تاریخچه‌ی کامل هر ردیف همیشه قابل بازسازی باشد.

## اجرای محلی بدون Docker (اختیاری، برای توسعه)

```bash
npm install
cp .env.example .env
# مقادیر .env را با آدرس LDAP خودتان تنظیم کنید
npm start
```
