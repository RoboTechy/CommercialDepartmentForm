# فرم مشترک فنی / بهره‌بردار / انبار کارفرما / بازرگانی غدیر

وب‌سرویس ثبت فرم چند بخشی که هر بخش آن فقط توسط پرسنل همان بخش (بر اساس عضویت گروهی در LDAP)
قابل تکمیل است. احراز هویت با پروتکل **LDAP** انجام می‌شود و کل سرویس داخل **Docker** اجرا می‌گردد.

## بخش‌های فرم

| بخش | کلید داخلی | گروه LDAP پیش‌فرض |
|---|---|---|
| فنی | `technical` | `technical` |
| بهره‌بردار | `operator` | `operator` |
| انبار کارفرما | `warehouse` | `warehouse` |
| بازرگانی غدیر | `commercial` | `commercial` |

کاربری که عضو گروه `formadmin` باشد (قابل تغییر با `LDAP_GROUP_ADMIN`) به همه‌ی بخش‌ها دسترسی تکمیل دارد.
سایر کاربران فقط بخش مربوط به گروه خودشان را می‌بینند به‌صورت قابل ویرایش؛ بقیه‌ی بخش‌ها را
فقط می‌توانند مشاهده کنند (خواندنی) و امکان ثبت/ویرایش آن‌ها را ندارند. این کنترل هم در
رابط کاربری و هم در سمت سرور (روی هر درخواست POST) اعمال می‌شود.

## اجرا با Docker (شامل یک سرور LDAP تستی)

```bash
docker compose up --build
```

این دستور سه سرویس بالا می‌آورد:

- **openldap** – یک سرور OpenLDAP تستی با کاربران و گروه‌های نمونه (فایل `ldap/bootstrap.ldif`)
- **phpldapadmin** – پنل مدیریت وب برای مشاهده/ویرایش کاربران LDAP در آدرس http://localhost:8081
  (Login DN: `cn=admin,dc=example,dc=com` رمز: `adminpassword`)
- **web** – وب‌سرویس فرم، در آدرس http://localhost:3000

### کاربران تستی

| نام کاربری | رمز عبور | دسترسی |
|---|---|---|
| `tech1` | `tech1Pass1` | تکمیل بخش فنی |
| `oper1` | `oper1Pass1` | تکمیل بخش بهره‌بردار |
| `wh1` | `wh1Pass1` | تکمیل بخش انبار کارفرما |
| `com1` | `com1Pass1` | تکمیل بخش بازرگانی غدیر |
| `admin1` | `admin1Pass1` | تکمیل همه‌ی بخش‌ها (مدیر سیستم) |

می‌توانید وارد شوید (مثلاً با `tech1`)، یک فرم جدید بسازید، و ببینید فقط بخش «فنی» برایتان
قابل تکمیل است و بقیه بخش‌ها به‌صورت خواندنی و قفل نمایش داده می‌شوند. با کاربر دیگری وارد شوید
تا تکمیل سایر بخش‌ها را ببینید.

## اتصال به سرور LDAP واقعی سازمان (Active Directory یا OpenLDAP)

سرویس `openldap` در `docker-compose.yml` فقط برای تست/دمو است. برای اجرای واقعی روی سرور:

1. سرویس `openldap` و `phpldapadmin` را از `docker-compose.yml` حذف کنید (یا کامنت کنید).
2. متغیرهای محیطی زیر را در سرویس `web` با اطلاعات LDAP واقعی سازمان جایگزین کنید:

   - `LDAP_URL` – آدرس سرور LDAP سازمان، مثلاً `ldaps://ldap.company.local:636`
   - `LDAP_BIND_DN` / `LDAP_BIND_PASSWORD` – یک حساب سرویس با دسترسی فقط-خواندنی جهت جستجو
   - `LDAP_USER_BASE` – DN پایه‌ی جستجوی کاربران، مثلاً `ou=Users,dc=company,dc=local`
   - `LDAP_GROUP_BASE` – DN پایه‌ی جستجوی گروه‌ها
   - `LDAP_USERNAME_ATTRIBUTE` – در Active Directory معمولاً `sAMAccountName`
   - `LDAP_GROUP_TECHNICAL` / `LDAP_GROUP_OPERATOR` / `LDAP_GROUP_WAREHOUSE` / `LDAP_GROUP_COMMERCIAL` / `LDAP_GROUP_ADMIN`
     – نام (`cn`) گروه‌های واقعی سازمان که هر بخش را نمایندگی می‌کنند

3. گروه‌های سازمانی شما باید از نوع `groupOfNames` (دارای ویژگی `member` با DN کامل کاربر) باشند؛
   اگر سازمان شما از گروه‌های `posixGroup` (ویژگی `memberUid`) استفاده می‌کند، فیلتر جستجوی گروه در
   `src/ldap.js` باید متناسب با آن تغییر کند (فقط چند خط).
4. برای Active Directory معمولاً از `ldaps://` (پورت 636) با گواهی معتبر استفاده کنید.
5. یک `SESSION_SECRET` تصادفی و طولانی برای محیط تولید تنظیم کنید.

## نکات فنی مهم برای استقرار واقعی روی سرور

- داده‌های فرم به‌صورت فایل JSON در `data/forms.json` نگهداری می‌شود (با `volume` جدا از ایمیج
  Docker). برای حجم بالا یا چند نمونه هم‌زمان از سرویس، جایگزینی با یک دیتابیس واقعی (PostgreSQL/MySQL)
  توصیه می‌شود.
- سشن کاربران در حافظه (MemoryStore) نگهداری می‌شود؛ اگر بیش از یک نمونه (replica) از سرویس اجرا
  می‌کنید، باید از یک session store مشترک (مثل Redis) استفاده کنید.
- تمام درخواست‌های ثبت/ویرایش هر بخش، سمت سرور هم کنترل دسترسی می‌شوند (نه فقط مخفی‌کردن دکمه در
  رابط کاربری)، بنابراین حتی با دستکاری درخواست HTTP هم امکان دور زدن محدودیت وجود ندارد.

## اجرای محلی بدون Docker (اختیاری، برای توسعه)

```bash
npm install
cp .env.example .env
# مقادیر .env را با آدرس LDAP خودتان تنظیم کنید
npm start
```
